1. Project Overview
The ERP Predictive Workforce Optimization system is an artificial-intelligence based prototype designed to support Human Resources and operational workforce planning.

The application combines:

Machine Learning for predicting the number of labor hours required by incoming ERP work orders.
Operations Research for determining which employees should be assigned to those tasks.
Cost analysis for comparing optimized workforce allocation against a simpler manual scheduling strategy.
Workforce analytics for identifying employees with excessive or insufficient utilization.
Interactive ERP planning through a Streamlit web interface.
The system follows a predictive-to-prescriptive architecture:

ERP Work Orders → Data Preparation → ML Forecast → Predicted Labor Hours → Optimization → Workforce Allocation → Cost & HR Analysis

The main purpose is not simply to predict workload, but to use those predictions to make workforce allocation decisions.

2. Project Objectives
The primary objective is to develop a prototype ERP workforce-planning module capable of answering two questions:

How much workforce capacity will incoming work require?

and:

Which employees should perform that work?

The specific objectives are:

Forecast required labor hours.
Compare two machine-learning regression models.
Evaluate model performance using MAE, RMSE and R².
Provide an interactive ERP planning interface.
Match employees to tasks according to skill requirements.
Respect employee working-hour limits.
Account for overtime.
Consider employee task preferences.
Consider task priority.
Minimize workforce labor cost.
Compare AI optimization against a manual baseline.
Calculate workforce utilization.
Identify employees who may be overloaded or underutilized.
Provide HR-oriented recommendations.
Produce a downloadable Google Colab notebook.

7. Data Encoding
The categorical department feature is converted using one-hot encoding:

pd.get_dummies()

This converts department categories into numerical variables that can be processed by the machine-learning models.

The prediction function then reindexes the generated features to ensure that the prediction data matches the columns used during training.

This is particularly important because a new ERP input may contain a different combination of departments from the training dataset.

8. Model Evaluation
The application calculates three main regression metrics.

MAE — Mean Absolute Error
MAE measures the average absolute difference between predicted and actual workload.

Lower MAE indicates better prediction accuracy.

The result is expressed in hours.

RMSE — Root Mean Squared Error
RMSE gives greater importance to large prediction errors.

Lower RMSE is preferred.

R² — Coefficient of Determination
R² measures the amount of variance in the target variable explained by the model.

The project requirement is interpreted as:

R² ≥ 0.85

However, because this prototype generates its own synthetic data, the actual R² value must be obtained by running the application.

The documentation should therefore report the measured value rather than claiming a predetermined result.

13. Workforce Optimization
The optimization engine uses:

Google OR-Tools

and specifically the linear solver interface with the SCIP optimization backend.

The optimization problem is formulated as a Mixed Integer Programming problem.

14. Decision Variables
For every task and employee combination, the model creates a binary variable:

x(i,j)

where:

1 = employee j performs task i
0 = employee j does not perform task i
Overtime is represented by a continuous variable for each employee.

15. Optimization Constraints
Constraint 1 — Every Task Must Be Assigned
Each task must receive exactly one employee.

Therefore:

Sum of employee assignment variables = 1

for each task.

Constraint 2 — Skill Compatibility
If an employee's skill level is below the required skill level of a task, the assignment variable is forced to zero.

Therefore, an employee cannot be assigned work beyond their configured skill level.

Constraint 3 — Employee Capacity
Each employee has:

Regular capacity.
Overtime capacity.
The total predicted workload assigned to an employee cannot exceed their combined available capacity.

Constraint 4 — Overtime
The optimization engine calculates how many assigned hours exceed the employee's regular capacity.

These hours are treated as overtime.

16. Optimization Objective
The optimizer attempts to minimize total workforce cost.

The assignment cost includes:

Predicted task hours.
Employee hourly rate.
Employee preference incentives.
Task priority incentives.
Overtime also receives an additional cost.

The objective therefore attempts to balance:

Low labor cost + suitable employee assignment + priority + preferences + capacity

17. Employee Preferences
Employees can specify preferred task IDs.

For example:

102,103

indicates that the employee prefers tasks 102 and 103.

The optimization model provides a configurable preference bonus.

This allows the user to determine how strongly employee preferences should influence scheduling.

18. Task Priority
Task priority is represented as:

Priority	Meaning
1	Highest
2	Medium
3	Lower

The optimization objective provides a stronger reward to higher-priority tasks.

The priority weight can be changed through the sidebar.

19. Overtime Configuration
The user can change the overtime multiplier.

The default value is:

1.5×

For example, if an employee earns $40/hour, overtime is calculated at:

$40 × 1.5 = $60/hour

The slider allows different overtime assumptions to be tested.

20. Manual Baseline
To demonstrate the value of optimization, the system calculates a manual baseline.

The baseline uses a much simpler strategy:

Identify employees who meet the required skill.
Select the cheapest eligible employee.
Consider available capacity.
Use overtime where required.
Calculate the resulting labor cost.
The baseline does not globally optimize the entire workforce.

The AI optimizer, in contrast, considers all assignments simultaneously.

This creates a meaningful comparison between:

Greedy/manual scheduling

and:

Global optimization.

21. Cost Analysis
The application calculates:

Manual baseline cost.
AI optimized cost.
Estimated savings.
Savings percentage.
The savings calculation is:

Savings = Manual Baseline − AI Optimized Cost

and:

Savings % = Savings / Manual Baseline × 100

Because the current project uses synthetic data, these savings should be described as:

illustrative simulated savings

rather than a real-world financial forecast.

22. Workforce Utilization
Employee utilization is calculated using:

Utilization = Total Assigned Hours / Total Available Capacity × 100

Total capacity consists of:

Regular Hours + Overtime Capacity

The system then categorizes employees approximately as:

90% or above: highly utilized.
35% or below: potentially underutilized.
Between these levels: generally balanced.
23. HR Recommendations
The system automatically generates recommendations.

For highly utilized employees, the application recommends considering:

Task reallocation.
Additional workforce capacity.
Reduced future workload.
For employees with low utilization, the system identifies them as candidates for:

Additional compatible work.
Reallocation from overloaded employees.
If utilization is balanced, the application reports that no immediate reallocation is recommended.

29. Why a GPU Is Not Required
The application uses tabular regression rather than a deep neural network.

The current dataset contains only:

1,800 samples

and the models use:

160 trees

for XGBoost and Random Forest.

Consequently, a normal modern CPU is sufficient for training and inference.

The OR-Tools optimization problem is also small enough for CPU execution.

30. Performance and Caching
The application uses:

@st.cache_resource

for model training.

This prevents Streamlit from unnecessarily retraining the ML models every time the interface is interacted with.

The optimization process also uses a session-state signature to avoid repeatedly solving the optimization problem when relevant inputs have not changed.

This improves application responsiveness.

36. Important Technical Limitations
The current prototype has several limitations that should be acknowledged in the final academic report.

Synthetic Training Data
The ML dataset is generated programmatically.

Therefore, the model does not represent real organizational workforce behavior.

Synthetic Target Variable
The actual_hours target is generated using a predefined mathematical relationship.

This means that model performance may be considerably easier to achieve than with noisy real-world ERP data.

Limited Employee Attributes
Real workforce allocation normally requires more information, such as:

Availability.
Vacation.
Sick leave.
Shift schedule.
Location.
Certifications.
Department membership.
Current workload.
Employment status.
These are not currently modeled.

Simplified Optimization
The optimization model assigns entire tasks to a single employee.

A production ERP system may need to support tasks being divided between multiple employees.

Simplified Scheduling
The current system optimizes workload allocation but does not create a detailed calendar schedule containing:

Start times.
End times.
Shift dates.
Breaks.
Holidays.
Employee availability windows.
Synthetic Cost Savings
Cost savings are simulated and should not be presented as guaranteed real-world savings.
